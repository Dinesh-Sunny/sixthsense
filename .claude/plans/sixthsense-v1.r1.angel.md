### 1 Weave EvaluationLogger around each run: one Evaluation per (mode, run) in the Evals tab · severity: high
Claim: the self-check already produces the W&B-judge-friendly artifact (prediction + grade per clip), but the plan only emits op traces and defers evals as `later` because `weave.Evaluation` "needs dataset of clips" (brief-llm Opportunities, plan leverage row weave). `weave.EvaluationLogger` is the imperative path: no Dataset, no Model class, no scorer ops. After `run_mode` finishes (single thread, outside the TaskGroup), log one prediction per verified incident and a summary. Result: a real Evaluation object with per-clip rows, a `came_true` score and an accuracy summary, visible in Weave Evals and comparable across runs. This is the cheapest "agents/evals" proof for the W&B judges and uses the same data already stored.
Evidence: `weave/__init__.py:87,121` exports `EvaluationLogger`; `weave/evaluation/eval_imperative.py:694-743` (docstring: evaluation starts at first `log_prediction`, ends at `log_summary`), `:744-751` ctor `EvaluationLogger(name, model, dataset, eval_attributes, scorers, trace_scores)`, `:1074` `log_example(inputs, output, scores)`, `:1113` `log_summary(summary)` auto-summarizes score means/fractions, `:902` `ui_url`. Docs (fetched): docs.coreweave.com/products/wandb/weave/guides/evaluation/evaluation_logger.md - "Evals tab, select evaluations, Compare". `wv-evaluation` is the outline's next-step-up and requires only `wv-tracing`, which the plan adopts fully (weave.yaml wv-eval `requires: [wv-tracing]`); `EvaluationLogger` is not in the outline (add it).
Suggested change (Implementation step 2 + `tracing.py` + Library table "tracing"): add `tracing.log_evaluation(mode, run_id, incidents) -> str | None` (the sanctioned weave importer): `EvaluationLogger(name=f"{mode}-{run_id}", model="cosmos3-reason-video", dataset=f"{mode}-clips", eval_attributes={"mode": mode})`; per incident `log_example(inputs={"clip": id, "mode": mode}, output={"what_next": ..., "risk": ...}, scores={"came_true": 1.0|0.5|0.0, "verified": 1.0})` (skip `unknown`); `log_summary({"accuracy": ..., "checked": ...})`. Run via `anyio.to_thread` (sync, network). No-op when untraced. Keep `unknown` rows out of the score (code-style: unknown, not zero). Store `eval_url` (= `ui_url`) on `ModeMetrics` (optional field) for point 5. Test: with no weave client the function returns None and calls nothing (plain function, no network). Unverified live: Evals-tab rendering of a logger-created eval, check once at step 5. Cost: ~30 lines, 0 deps, ~0 extra GPU calls.

### 4 Make VastDB visibly the system of record: scalar grade columns, server-side metrics, a `runs` history table · severity: medium
Claim: the data brief puts everything except 5 scalars into a `payload` blob, so `/api/metrics` (candidates, came_true yes/partly, accuracy) must read every payload and compute in Python; VAST judges would see an expensive JSON-in-a-table pattern. Adding `came_true` (utf8), `camera_id` (utf8) and `source` (utf8, join key to `vss-collection`) as scalar columns lets metrics be a column-only select with ibis predicates (`_.came_true == "yes"`), exactly the pushdown VastDB sells, and an insert-only `runs` table (`run_id, mode, started_ms, checked, accuracy, eval_url`) gives an accuracy-over-runs history ("it gets graded every run, stored where the footage lives") with no upsert logic.
Evidence: brief-data lines 11-14 (columns id/mode/risk/verified/updated_ms + payload; "list/mode filtering still server-side"), lines 17-19 (type probe covers utf8/int64/float64, already validated by the probe), vdb-select `columns=` and vdb-predicate (`vastdb.yaml:129-143`), `alerts` is already insert-only with the same shape (brief-data line 13), `vdb-sort-client` for ordering. No vector columns involved.
Suggested change (plan Library row "store", brief-data Table design, contracts `ModeMetrics`): add the three columns and the `runs` table to the DDL and to the step-1 type probe; `metrics()` = `select(columns=["mode","verified","came_true"], predicate=...)`; append one `runs` row at the end of `run_mode`. README/architecture.md: one diagram "footage + vectors + incidents + grades + runs, all in VastDB". Test: JsonStore and the fake VastStore return identical metrics from the same fixtures.
